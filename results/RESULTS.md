# 自前の実測結果（2026-09-18）

実行: Mac（東京の自宅回線）とクラウドコンテナ（米国側）の2拠点。合計 **2,320 リクエスト、入力 1,486,076 トークン、$0.0624**（出力は無料）。エラー0件。
モデルは `jev-latest`（= jev-1.13.0）。ログは `logs/*.jsonl` に全件。

## 何を測ったか

題材は **Claude Code のハーネス選択**。作業依頼の文面を読んで、4つの実行先のどれに渡すかを決める。

- `haiku_inline` 小さく機械的な変更。軽量モデルにその場で直させる
- `opus_subagent` 実装方針そのものを選ぶ判断が要る。上位モデルのサブエージェントへ
- `external_harness` 複数箇所にまたがるか作業量が大きい。長時間動く外部ハーネスへ
- `ask_user` 情報が足りない、または取り消しの効かない操作を含む。依頼者に確認

シナリオは5つの属性（情報の有無 / 不可逆操作の有無 / 設計判断の有無 / 変更範囲 / 作業量）の全組み合わせから、決定論スクリプトで120件を生成。**正解ラベルはルールで確定させていて、モデルにもLLMにも作らせていない**。各ラベル30件ずつの均衡設計。日本語版・英語版・無関係な雑談を1〜2文混ぜた版を、同じシナリオから生成した。

2つの聞き方を比べた。

- **direct**: 4択の Choice を1回投げる
- **decomposed**: 前提条件を4つの Noul（情報が特定できるか / 不可逆操作を含むか / 設計判断が要るか / 変更が広いか）にして**1リクエストに並列で入れ**、返ってきた確率をコード側で同じルールに通す

## 結果1: 同じモデル・同じ入力で、48.3% と 98.3%

日本語・雑談なし（Mac、各120件）

- direct 48.3%
- decomposed 98.3%

英語・雑談なし

- direct 56.7%
- decomposed 99.2%

日本語・雑談あり

- direct 55.0%
- decomposed 86.7%

英語・雑談あり

- direct 65.0%
- decomposed 96.7%

クラウド側でも同じ（日本語・雑談なしで 48.3% / 97.5%）。拠点を変えても数字は動かない。

## 結果2: 個別の条件は100%読めている

decomposed で投げた4つの Noul を、シナリオ生成時の属性（真値）と突き合わせた。日本語・雑談なし・閾値0.5。

- 情報が特定できるか: 120/120 = 100%
- 不可逆な操作を含むか: 120/120 = 100%
- 設計判断が要るか: 120/120 = 100%
- 変更が広いか: 112/120 = 93.3%

**一つずつ聞けば全部読めている。同じ文章を4択で一度に聞くと48.3%まで落ちる。** モデルの理解力ではなく、聞き方の問題だという一番強い証拠がこれ。

## 結果3: 間違え方は「軽い方に流す」

日本語・雑談なし・direct の予測分布（正解は各30件ずつ）

- haiku_inline に 71件（正解30件）
- external_harness に 25件
- opus_subagent に 13件
- ask_user に 11件

ラベル別の再現率（direct / decomposed）

- haiku_inline: 30/30 / 30/30
- opus_subagent: 6/30 / 30/30
- external_harness: 11/30 / 28/30
- ask_user: 11/30 / 30/30

**`ask_user` が30件中19件取りこぼされた。そのうち12件は本番テーブルの物理削除や main への force push を含む依頼だった。**（残り10件は情報不足の依頼。重複あり）decomposed では取りこぼし0件。

## 結果4: 雑談を混ぜると、分解した方が壊れる

日本語で雑談を1〜2文混ぜると、decomposed は 98.3% → 86.7% に落ちた。落ち方はラベル別で偏っていて、external_harness が 28/30 → 20/30、opus_subagent が 30/30 → 25/30。ask_user は 30/30 のまま。
英語では 99.2% → 96.7% で軽微。**日本語 × 無関係な文脈 × 分解**が一番弱い組み合わせだった。
direct は逆にわずかに上がった（48.3% → 55.0%）が、これは予測分布が少し平準化して偶然の一致が増えただけで、ラベル別に見ると改善していない。

## 結果5: confidence は順位付けには使えるが、確率としては信用できない

direct の confidence 帯ごとの実正解率（Mac、全960件のうち direct 480件）

- 0.1-0.2 帯: 50.0%（n=14）
- 0.2-0.3 帯: 31.4%（n=35）
- 0.3-0.4 帯: 36.1%（n=61）
- 0.4-0.5 帯: 22.8%（n=57）
- 0.5-0.6 帯: 44.4%（n=54）
- 0.6-0.7 帯: 48.8%（n=41）
- 0.7-0.8 帯: 50.0%（n=36）
- 0.8-0.9 帯: 55.8%（n=43）
- 0.9-1.0 帯: 94.9%（n=138）

0.9以上はよく当たる。それ以下は帯を上げても正解率がほとんど上がらず、0.4帯が0.2帯より悪いところもある。**「confidence 0.7 なら7割正しい」という読み方はこのタスクでは成り立たない。**

## 結果6: 閾値で守ろうとすると、保留だらけになる

日本語・雑談なし・direct で、confidence が閾値以上のものだけ自動処理した場合

- 0.50以上: 自動65.0%、その中の正解率60.3%、保留35.0%
- 0.70以上: 自動49.2%、正解率72.9%、保留50.8%
- 0.80以上: 自動40.0%、正解率79.2%、保留60.0%
- 0.90以上: 自動32.5%、正解率84.6%、保留67.5%
- 0.95以上: 自動25.8%、正解率96.8%、保留74.2%

96.8%の精度を買おうとすると、4件に3件が人間待ちになる。**一方 decomposed は保留ゼロで98.3%。**同じモデルで、聞き方を変えただけ。

## 結果7: レイテンシは往復込みで東京 p50 544ms

直列50回ずつ（Mac＝東京の自宅回線 / クラウド＝米国側、ただしプロキシ経由）

- Choice 1問: Mac p50 544.5ms / p95 615.3ms / p99 788.5ms、クラウド p50 413.3ms
- Noul 1問: Mac p50 551.2ms、クラウド p50 435.6ms
- **Noul 4問を1リクエストに並列: Mac p50 549.2ms、クラウド p50 423.8ms**
- Score 1問: Mac p50 546.4ms、クラウド p50 431.9ms

公式の「70ms〜500ms」は往復を含まない値。東京から叩くと p50 で 544ms、p99 で 788ms。**4問並列にしてもレイテンシはほぼ変わらない**（549ms 対 551ms）。増えるのは入力トークンだけ（445 → 803）。

## コスト

- direct 1件あたり入力640トークン ≒ $0.0000269
- decomposed 1件あたり入力854トークン ≒ $0.0000359（33%増）

## この実験の限界（記事に必ず書く）

1. **decomposed の4つの質問は、シナリオ生成に使ったルールと同じ分解になっている。** 分解がタスク構造と一致している理想ケースで、有利になるのは設計上そうなる。agentjournal.dev の「テストが無価値だった。ひとつの質問が既に答えを目の前に持っていた」と同じ穴が、ここにも半分ある。
   ただし、direct にも全く同じ4条件を説明文として渡してあり（4択の各選択肢の説明がそれ）、情報量は同じ。**同じ情報を1問で聞くか4問で聞くかの違いだけで50ポイント動いた**、という読み方は成り立つ。
2. **質問文の長さが揃っていない。** direct の質問部分は325字、decomposed は664字（入力トークンで 640 対 854）。分解側は条件ごとに例示まで書けるので、「条件を割った効果」と「説明を厚く書いた効果」がこの実験では分離できていない。渡している判断材料（4条件）は同じだが、記述量は同じではない。
3. **合成シナリオであって本番ログではない。** 実際の依頼文はもっと曖昧で、ラベルが一意に決まらない。
3. **n=120 のタスク1つ。** 他ドメインで同じ比になるとは限らない。
4. 閾値0.5は仮置き。合成ルールの閾値を振ると 0.4で97.5%、0.5で98.3%、0.6で91.7%、0.7で79.2%（日本語・雑談なし）。
5. クラウド側の計測は HTTPS プロキシを経由しているので、純粋な米国リージョンからの値ではない。
